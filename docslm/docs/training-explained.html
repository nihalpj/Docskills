How model training actually works

From “a model is a pile of numbers” to “here is the shipped, quantized model file” — the training loop, the main families of training, and what you get at the end. Illustrated with our real DocSLM-0.8B run (fine-tuning Qwen3.5-0.8B on one RTX 4090).

1 The big idea: a model is a function full of knobs

A language model is just a very large mathematical function. Its weights (≈0.8 billion numbers for DocSLM) are adjustable knobs. The function’s job: read some tokens, predict the next token. Training is the process of wiggling the knobs so the predictions get better — measured example by example.

Untrained

Random knobs → gibberish

At initialization the weights are random noise. The model outputs random characters. It has never seen language.

Pretrained

Trained on trillions of tokens

After pretraining the model can write fluent text and knows facts — but it doesn’t yet follow instructions or use tools reliably. This is where we start: Qwen3.5-0.8B.

Fine-tuned

Nudged toward one job

Fine-tuning adjusts the same knobs with a much smaller, purpose-built dataset so the model behaves like the thing you actually want — for us, a document-skills agent.

2 The training loop: five steps, repeated thousands of times

Every training method in section 3 — pretraining, SFT, DPO, all of them — runs the same core loop. The only things that differ are what the examples look like and how the error is scored.

What is a gradient?

For every weight, the backward pass answers: “if this number went up a little, would the loss get better or worse, and how fast?” That direction-and-steepness value is the gradient. The step simply moves each weight slightly the helpful way.

What is a checkpoint?

A snapshot of all weights + optimizer state written to disk every N steps (ours: every 200). It lets you resume after a crash — and, crucially on a rented GPU, it means an interruption costs you minutes, not the whole run.

Why is loss only on assistant tokens?

In SFT we mask the prompt and tool results to −100 so the model is graded only on what it must produce itself (think-blocks, tool calls, answers). See the diagram in section 3.

3 The different types of training

Same loop, different data and scoring. They build on each other in stages — a base model becomes an instruct model becomes your model. For each of the six you’ll actually encounter: what it means in plain words, then the trade-offs you’re accepting when you choose it.

Stage 0 — done by the lab, not you

Pretraining

What it means: the model learns language from absolute scratch by playing one simple game — predict the next token — trillions of times over web text, books and code. Every fact, grammar rule and programming idiom it will ever “know” gets compressed into its weights here. The output is the base model everyone else starts from (for us: Qwen3.5-0.8B-Base).

Pros

  • No labels needed — any text is training data (self-supervised)
  • Builds general language, world knowledge and code ability
  • Reliably improves with more data and compute (scaling laws)

Cons

  • Costs millions of dollars and weeks on huge GPU clusters
  • Result only continues text — won’t follow instructions or call tools
  • Knowledge frozen at the data’s cutoff date
  • Off the table for individuals — you always start from someone’s base model
Stage A — optional

Continued pretraining (CPT)

What it means: more pretraining — the same “predict the next token” game — but on a narrow, domain-specific corpus instead of the whole internet. For DocSLM that’s ~3B tokens of docx-js / openpyxl / ReportLab docs, OOXML internals and document-generation code, so the target domain stops looking like a foreign language before behavior training begins.

Pros

  • Cheaply teaches domain vocabulary, API idioms and file formats
  • No labels required — raw domain text is enough
  • Lets the SFT stage spend its budget on behavior, not vocabulary

Cons

  • Catastrophic forgetting: general skills degrade while it learns the domain
  • Needs ~1–10B quality tokens before it does anything measurable
  • Benefit is indirect — you can’t confirm it helped until after SFT
  • Often unnecessary: our pipeline runs it only if the SFT pilot shows >20% library-API errors
Stage B — our main event

Supervised fine-tuning (SFT)

What it means: learning by imitation. You write (or generate-and-verify) thousands of perfect example conversations — user asks, assistant answers with exactly the right think-block, tool call and summary — and the model is graded only on its own tokens (loss-masking diagram above). It learns to reproduce the demonstrated behavior: the format, the process, and when to stop.

Pros

  • Most direct, reliable way to teach a specific behavior or output format
  • Small data works — our whole run: 930 trajectories, ~1 hour, <$1 on a 4090
  • Predictable and verifiable: check the examples, you know exactly what’s taught

Cons

  • Capped by teacher quality — it imitates the demos, weaknesses included
  • Can’t rank “good” vs “great”: every demo is treated as the right answer
  • Overfits on small data — the validation curve is your guardrail
  • Data curation is the real cost; one bad batch teaches bad habits fast
Variant of SFT

LoRA / QLoRA (parameter-efficient)

What it means: instead of moving all 0.8B weights, freeze the original model and learn a couple of tiny adapter matrices (A·B) beside each layer — only ~1% of parameters train (diagram below). QLoRA is the same trick with the frozen base compressed to 4-bit, so even a 7B model fits a small GPU. Afterwards the adapters merge back in — or swap like plug-ins.

Pros

  • Tiny memory footprint — trains where full FT can’t (12–16 GB GPUs)
  • Adapter = megabytes: cheap to store, share, and stack many per base
  • Fast iteration; often “good enough” for style and format tasks

Cons

  • Usually a few points below full FT on hard tasks (ours: −3–6 pts on gate A)
  • QLoRA’s 4-bit base adds quantization noise on top
  • Weaker for deep skill changes — teaches manner more than muscle
  • Little upside for tiny models: our 0.8B full FT is already cheap, so it’s only a fallback here
Stage C

Preference tuning: RLHF · DPO · GRPO

What it means: SFT says “here is the right answer”; preference tuning says “here are two answers — this one is better.” RLHF first trains a reward model from human ratings, then optimizes the model against it with reinforcement learning (PPO). DPO skips the reward model and learns directly from (chosen, rejected) pairs. GRPO has the model generate a group of candidate attempts and scores each one programmatically — did the script run? did postcheck pass?

Pros

  • Teaches judgment — picking the better answer, tone, concision, safety
  • GRPO with verifiable rewards can exceed the teacher’s demonstrations
  • DPO is simple and stable: one stage, one dataset of pairs

Cons

  • Reward hacking: the model games the metric (empty docs that pass postcheck)
  • RLHF needs a separate reward model + RL infra — famously fragile (PPO)
  • Over-optimization degrades SFT skills (the “alignment tax”)
  • GRPO needs a live sandbox + eval harness; pair data is expensive to build
Cross-cutting

Knowledge distillation

What it means: a big, expensive teacher model produces the training material — answers, reasoning traces, grades — and a small student is trained to reproduce that quality, packing capability into a model that’s cheap to run forever after. DocSLM is distillation-shaped end to end: a frontier teacher writes and repairs trajectories, execution verifies them, and the 0.8B student learns the result.

Pros

  • Small models punch far above their parameter count
  • Teacher can generate nearly unlimited supervised data
  • Near-frontier quality at cents per query — the whole point of DocSLM

Cons

  • Student is capped by teacher quality and the training recipe
  • Inherits teacher quirks and verbosity along with the skill
  • Teacher generation isn’t free (~$6–10k in our pipeline estimate)
  • Some skills don’t compress — hence the cascade to a frontier model

4 The end result: what actually comes out

Training does not produce “an app” or “an AI”. It produces a folder of learned numbers — plus the evidence that they’re better than before. Everything else (serving, latency, product) is engineering wrapped around that folder.

What changes: before vs after fine-tuning

The full deliverable, not just weights

A shippable model is more than safetensors:

📦 Artifacts — bf16 checkpoint · GGUF Q4_K_M / Q8_0 · AWQ int4

🧾 Lineage card — seed, data manifest hash, hyperparameters, env digests (reproducibility contract)

📏 Eval report — DocBench execution, judge acceptance, repair rate, cascade rate; gates re-checked on the quantized build

🔌 Integration — llama.cpp / vLLM serving recipe + the agent-runtime adapter that routes to it, escalating to a frontier model when its verifier fails twice

6 Glossary — the ten words that unlock everything else

Token
A chunk of text (~¾ of a word) — the atomic unit models read and predict.
Weights
The model’s learned numbers; “training” = updating them. 0.8B of them here.
Forward pass
Running input through the model to get predictions.
Loss
One number scoring how wrong the predictions were; training minimizes it.
Gradient
Per-weight direction+steepness of “how to get less wrong”, computed by backpropagation.
Optimizer / LR
The rule for turning gradients into weight updates; learning rate = update size.
Batch / epoch
Examples per step / one full pass over the dataset (we: effective batch 32, 3 epochs).
Overfitting
Memorizing training examples; spotted when validation loss rises while train loss falls.
Checkpoint
A saved snapshot of weights you can resume from — your insurance on rented GPUs.
Inference
Using the trained model (no weight updates); what your users actually run.
